# R0-WS2-010 — CI where the failure is silent

Spans two repositories. `platform-skills` holds the other half; the spec is here because
the story's `repo` is `platform-workflows` and one spec that describes both is better than
two that can disagree.

## The question this story is an answer to

Five repositories had no CI, and the reason given for adding it to all five was that they
all contained files. That is a habit rather than a reason, and when it was challenged the
better question turned out to be **what actually breaks, and would anyone notice?**

Three of the five fail *loudly*, and were deliberately left alone:

| Repository | Why not |
|---|---|
| `sdlc-work-tracker` | 297 lines of Python. A syntax error announces itself the moment it runs, to the one person running it. |
| `sandbox-images` | Four manifests. Invalid YAML is rejected by `kubectl apply`; the real risk is a *semantically* wrong NetworkPolicy, which needs a live cluster CI has not got. Its case arrives with the Dockerfiles — image build and scan — inside `R0-WS3-003`. |
| `sdlc-docs-portal` | `make check` already exists and has caught real drift twice, but the valuable part reads sibling repositories from disk and a CI checkout has none. Revisit at `R0-WS1-003`. |

Two fail *silently*, and got CI. That distinction is the story's actual content — the
gates below are a consequence of it.

## `platform-workflows`

The repository whose README argues for `actionlint`, which had never run one. Every
repository in the polyrepo calls these workflows, so a bad commit here does not break one
build; it breaks all of them, at startup, with no jobs and no log to read.

**`actionlint`**, installed with `go install` at a pinned version rather than the upstream
`curl | bash`. The module checksum database verifies it and a download script verifies
nothing, which matters more here than anywhere: this is the one place where a substituted
linter would be reviewing everyone else's workflows.

**`tools/check-workflows.py`** covers the two things `actionlint` cannot know:

- A workflow here that omits `on: workflow_call` is not reusable, and the caller's error
  does not say that is why.
- Eleven repositories copy their call block out of the README. Rename an input, or add a
  required one, and every caller breaks while the README goes on showing the old shape —
  and it breaks in *their* repository, not this one. The check resolves every `uses:` in
  every `yaml` fence back to the workflow it names and compares `with:` against the
  declared inputs in both directions. It also rejects an example pinned to `@main`, which
  the README argues against two sections further down.

A bare `uses:`-only fragment — the "Pin the version you call" example — is exempt from the
input comparison. It is illustrating the reference, not the call.

## `platform-skills`

A skill with malformed front matter is skipped by Claude Code without an error. The session
starts, the review never runs, and the only symptom is a defect that gets through.

That is this platform's own history rather than a hypothetical: `R0-WS2-001` and
`R0-WS2-002` were both completed with no skill loading at all, and the audit afterwards
found nine defects they would have caught.

`tools/check-skills.py` asserts front matter on line 1, parsing, `name` matching its
directory, and a non-empty `description` — and two things beyond the file:

- **The published plugin id is literally `aisdlc@aisdlc`**, the string every repository
  has committed in `.claude/settings.json`. Rename either half here and all of them
  silently load nothing. The coupling spans repositories and a workflow's `GITHUB_TOKEN`
  reaches only its own, so it is asserted here, where both halves are visible.
- **The README table matches `skills/` on disk.** The table is the catalogue the docs
  portal's Marketplace section reads, so a skill missing from it is a skill nobody knows
  to use.

**Deliberately not checked: description length.** Claude Code has a bound and this file
does not know it. A rule with no source gets argued away the first time it is inconvenient
— which is the repository's own stated standard for adding one.

## What the checks found on their first run

**The README claimed 18 skills against 20 on disk**, and said "and fifteen more" where
three are named. Corrected.

**`actionlint` failed on `service-image.yml:86`** — SC2016, a `${{ }}` expression inside
single quotes. shellcheck is wrong about the mechanism, since GitHub substitutes the
expression textually before the shell sees the line, but right that the line is the wrong
shape: textual substitution into a script is how a value containing a quote or a `$(`
becomes code. The values now arrive through `env:`.

`cosign sign` on line 83 has the same shape and was left alone. That workflow has never
run, and churning a signing command for style inside a CI story is not a trade worth
making. It is the first thing to fix when `service-image.yml` is first exercised, at
`R0-ALL-003`.

## What it cost, and the lesson that stuck

`make lint` reported clean locally on the exact file CI then rejected. **`actionlint`
shells out to `shellcheck` for every `run:` block and skips that entire class of check,
without saying so, when shellcheck is not installed.** A local gate quietly weaker than CI
is worse than no local gate, so the target now fails outright when shellcheck is missing.

Two CI wait loops then hung, for the same reason in a different costume: `gh run list
--commit` needs the **full** SHA. Given the seven-character form it matches nothing, exits
0 and prints nothing — so the existing rule against `--limit 1` leads straight into
waiting for a run that can never appear.

Both are the same failure: **a check that reports success while checking nothing.** Which
is the thing this whole story is about, arriving twice in the tooling built to prevent it.
Both are now in the `ci-workflow-review` skill, and the habit they produced is to prove a
linter is wired in with a deliberate violation rather than by reading a green exit code.

## Acceptance

| Criterion | |
|---|---|
| A skill with broken front matter fails the build rather than being skipped in silence | **Met** — `name: security_review` against directory `security-review`, exit 1, re-run against the merged `main` |
| A renamed or added workflow input fails here rather than in the eleven repositories that call it | **Met** — `service` → `service-name` reported as both a missing required input and an undeclared one, exit 1, re-run against the merged `main` |

Five mutations were run against the skills check (leading blank line, name/directory
mismatch, empty description, renamed marketplace, a skill missing from the table) and each
was caught.

## What is not here

**Three repositories still have no CI**, on purpose, with the reasoning recorded above and
in the story's notes so it is not re-litigated. Two have a named trigger to revisit:
`sandbox-images` at `R0-WS3-003`, `sdlc-docs-portal` at `R0-WS1-003`.

**The skills check sees only its own repository.** The engineering-practice paragraph is
hand-copied into seven READMEs and every copy is stale — all seven say "18 skills". Only
`platform-skills`' own copy is fixed and guarded here. `sdlc-docs` is the one place with
every repository on disk, so the generator and the cross-repository check belong there:
`R0-WS2-011`.

## Definition of Done

Met, except **Deployed** in the sense of a service — this is CI, not a deployable artefact.
Both gates are running on `main` and green.
